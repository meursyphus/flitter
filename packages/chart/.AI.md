# Chart Package Architecture

## Overview

The chart package uses a **two-layer architecture**:

- **Headless layer** (`src/headless/`): Renderless chart logic that delegates all visual rendering to injectable `custom` functions. Chart type agnostic to visual style.
- **Styled layer** (`src/charts/`): Pre-built, ready-to-use charts that wire up specific `custom` implementations and config defaults for a named visual style (e.g., "toast").

```
import { BarChart } from "flitter-chart"        // styled chart (style-routed factory)
import { Headless } from "flitter-chart"         // headless charts namespace (Headless.BarChart, Headless.LineChart, ...)
```

## Headless Layer

### Purpose

Each headless chart owns the **structural logic** (data iteration, scale computation, widget tree composition) but delegates **all rendering** to `custom` functions. This makes the chart completely reskinnable without touching internals.

### Generic Config Pattern

Every headless chart is generic over `TConfig`:

```ts
// The context passed to every custom function
type BarChartContext<TConfig = {}> = {
  custom: BarChartCustom<TConfig>;
  data: BarChartData;
  scale: BarChartScale;
  title: string;
  direction: BarChartDirection;
  config: TConfig;   // <-- user-injected config, typed by the styled layer
};
```

The styled layer defines a concrete `TConfig` (e.g., `ToastBarChartConfig`) with colors, fonts, animation settings, etc. The headless layer passes it through untouched.

### Custom Functions

All custom functions share the same signature:

```ts
(args: T, context: ChartContext<TConfig>) => Widget
```

The headless `chart.ts` calls each custom function at the appropriate place in the widget tree. For example, `custom.bar({ value, label, legend, index }, context)` is called once per bar.

### Provider Pattern

The headless chart wraps its widget tree in a `Provider` so that deeply nested internal widgets can access the full `BarChartContext` via `BarChartConfigProvider.of(context)`. This avoids prop drilling through the internal widget tree.

### Default Implementations

Each headless chart has a `default/` subfolder with minimal custom implementations. These are used as fallbacks when the user or styled layer does not override a particular custom function. Defaults are merged: `{ ...defaults, ...userCustom }`.

### Available Headless Charts (18)

BarChart, LineChart, AreaChart, BubbleChart, ScatterChart, HeatmapChart, TreemapChart, FunnelChart, RadarChart, GaugeChart, StackedAreaChart, PieChart, SunburstChart, StackedBarChart, CandlestickChart, BoxPlotChart, WaterfallChart, SankeyChart

## Styled Layer

### Style Plugin Registry

Each chart type in `charts/` has a `plugin.ts` that maps style names to config types and factory functions:

```ts
// charts/bar-chart/plugin.ts
export type BarChartStyleMap = {
  toast: ToastBarChartConfig;
  // future styles go here
};

export const barChartStyles = {
  toast: ToastBarChart,
} as const;
```

### Style-Routed Factory

The top-level styled factory uses the `style` key to route to the correct implementation, with full TypeScript inference on `config`:

```ts
BarChart({ style: "toast", data, config: { colors: [...] } })
//                                ^^ TypeScript infers Partial<ToastBarChartConfig>
```

### How a Style Implementation Works

A style implementation (e.g., `charts/bar-chart/toast/index.ts`):

1. Defines a set of `custom` functions (one per chart component)
2. Merges config: `{ ...defaultToastConfig, ...userConfig }`
3. Merges custom overrides: `{ ...toastCustom, ...userCustom }` (user can override individual components)
4. Calls the headless chart factory with the merged values

Currently only `bar-chart/toast` is implemented. Other chart types will follow the same pattern.

## Adding a New Style (e.g., "material" for bar-chart)

1. **Create config**: `charts/bar-chart/material/config.ts`
   - Define `MaterialBarChartConfig` type with style-specific properties
   - Export `defaultMaterialConfig` with defaults

2. **Create custom components**: Individual files in `charts/bar-chart/material/`
   - Each file exports a function matching the `(args, context: BarChartContext<MaterialBarChartConfig>) => Widget` signature
   - Only override the components that differ from defaults

3. **Create style entry**: `charts/bar-chart/material/index.ts`
   - Assemble `materialCustom` object from individual component files
   - Export `MaterialBarChart` factory that merges config + custom, calls `HeadlessBarChart`

4. **Register**: Add to `charts/bar-chart/plugin.ts`
   - Add `material: MaterialBarChartConfig` to `BarChartStyleMap`
   - Add `material: MaterialBarChart` to `barChartStyles`

5. **Export types**: Add config type export in `charts/index.ts`

## Adding a New Styled Chart (e.g., line-chart)

1. Verify the headless chart (`headless/line-chart/`) supports the `TConfig` generic pattern
2. Create `charts/line-chart/` following bar-chart's structure:
   - `plugin.ts` with `LineChartStyleMap` and `lineChartStyles`
   - `index.ts` with style-routed factory
   - `toast/` (or other style) subdirectory with config, custom components, and entry
3. Export from `charts/index.ts`

## Key Patterns

- **Factory function exports**: Never export widget classes directly. Always wrap in a factory function.
- **Config merging**: `{ ...defaults, ...userConfig }` for config, `{ ...styleCustom, ...userCustom }` for custom overrides. User always wins.
- **Path aliases**: `@headless/*`, `@shared/*`, `@utils/*` (defined in `tsconfig.json`)
- **Shared cartesian components**: `src/shared/cartesian/` has reusable axis, grid, plot layout, and scale logic used across cartesian chart defaults.
- **Animation**: Styled layers handle animation (see `toast/bar-group.ts` using `AnimationController` + `Tween`). Headless charts are animation-agnostic.
