# なぜFlitterを使うべきか？

## あなたが直面している問題

月曜日の朝、SaaSスタートアップの開発チーム会議室。PMが新機能の要件を持ってやってきました。

> 「製品に**ワークフローエディタ**を追加する必要があります。ユーザーはノードをドラッグして接続でき、リアルタイムで更新されるようにしたいです。NotionやFigmaみたいな感じで！」

チームメンバーの顔が固まります。フロントエンド開発者が慎重に口を開きます。

> 「D3.jsを試すこともできますが...ノードの位置計算、接続線の描画、ドラッグ処理...基本機能だけでも2〜3週間はかかるでしょう。」

別の開発者が付け加えます：

> 「Canvas APIで直接描画すべきでしょうか？それともSVG？テキストはどう扱いますか？改行や配置を手動で計算しなければなりません...」

## 馴染みのあるフラストレーション

心当たりはありませんか？

ウェブ上で複雑なグラフィックスを扱うことは、常に開発者の悪夢でした。HTML/CSSには明確な限界があり、D3.jsやCanvas APIを使うのは、すべてを手動で計算しなければならない1990年代に戻るような感覚です。

簡単な例を見てみましょう：ボックス内でテキストを中央揃えにし、自動的に折り返すようにする。

### D3.jsでは、これほど複雑です：

```javascript
// 座標計算から始めて...
const svg = d3.select("svg");
const boxWidth = 200;
const boxHeight = 100;

// テキスト要素を作成して位置を設定
const text = svg.append("text")
  .attr("x", boxWidth / 2)
  .attr("y", boxHeight / 2)
  .attr("text-anchor", "middle");

// 改行のための複雑な関数を実装
function wrapText(text, width) {
  const words = text.text().split(/\s+/);
  const lineHeight = 1.2;
  let line = [];
  let lineNumber = 0;
  let tspan = text.text(null).append("tspan");
  
  words.forEach(word => {
    line.push(word);
    tspan.text(line.join(" "));
    if (tspan.node().getComputedTextLength() > width) {
      line.pop();
      tspan.text(line.join(" "));
      line = [word];
      tspan = text.append("tspan")
        .attr("x", boxWidth / 2)
        .attr("dy", lineHeight + "em")
        .text(word);
    }
  });
  
  // 垂直方向の中央揃えのための追加計算...
  const totalHeight = lineNumber * lineHeight * 16;
  text.attr("transform", `translate(0, ${-totalHeight/2})`);
}

// さらにリサイズイベントの処理も...
```

50行以上のコード、複雑な計算、それでも完璧ではない結果。これが2024年のウェブ開発だと信じられますか？

**驚くべき点**：Canvasレンダラーであるにもかかわらず、マウスカーソルが自動的に変わることに気づきましたか？ドラッグエリアではリサイズカーソルになります。Flitterはこれらすべての複雑な処理を行います。あなたはビジネスロジックに集中するだけです。

```typescript

```

## Flitterとは？

```
┌─────────────────────────────────────────────────┐
│               あなたのアプリ                        │
├─────────────────────────────────────────────────┤
│              ウィジェットレイヤー                    │
│         (Container, Text, Column...)             │
├─────────────────────────────────────────────────┤
│           RenderObjectツリー                      │
│     (レイアウト、ペイント、ヒットテスト)                │
├─────────────────────────────────────────────────┤
│          Flitterエンジンコア                       │
├─────────────┬───────────────────────────────────┤
│  SVGレンダラー  │       Canvasレンダラー             │
└───────────────┴─────────────────────────────────┘
```

Flitterは**ウェブ上で動作する宣言的UIレンダリングエンジン**です。FlutterのパワフルなウィジェットシステムをJavaScriptで実装しています。

### コア機能

#### 🎯 デュアルレンダラーシステム
- **SVG**: SEOフレンドリー、テキスト選択可能、CSSアニメーション
- **Canvas**: 高パフォーマンス、ピクセルレベルの制御、複雑なアニメーション

![svg-canvas](/svg-canvas.gif)

#### 🚀 業界初のSSR + Canvasハイドレーション
```typescript
// サーバーではSVGでレンダリング → クライアントでCanvasに切り替え
<Widget 
  renderer="canvas"
  ssr={{
    size: { width: 800, height: 600 }  // サーバーレンダリングサイズ
  }}
  widget={...} 
/>
```

SVGで高速な初期ロード、Canvasでスムーズなインタラクション。**これができるのはFlitterだけです。**

## 他のグラフィックスライブラリとの比較

### 😫 既存ライブラリの限界

| ライブラリ | 問題点 |
|---------|----------|
| **D3.js** | すべてを手動で計算。座標、サイズ、アニメーション... |
| **Konva.js** | オブジェクト指向だが依然として命令的。複雑なレイアウトは悪夢 |
| **Fabric.js** | キャンバス操作には良いが、UIコンポジションには不適切 |
| **Paper.js** | ベクターグラフィックスに強いが、一般的なUIには困難 |
| **Three.js** | 3Dには素晴らしいが... 2D UIにThree.js？ |

## 実際の本番環境で実証済み

### 🎯 ユースケース1：複雑なダイアグラムエディタ

**問題**：「100以上のノードでスムーズに動作するERDエディタを構築する必要があります」

**Flitterの解決策**：
```typescript
// ノードのドラッグ、接続の描画、自動配置...
// すべてウィジェットコンポジションで解決
Stack({
  children: [
    ...nodes.map(node => 
      Draggable({
        child: NodeWidget(node),
        onDrag: updateNodePosition
      })
    ),
    CustomPaint({
      painter: ConnectionPainter(connections)
    })
  ]
})
```

## なぜ今Flitterなのか？

### 📈 市場の需要
- SaaS製品の複雑化の増加
- ダッシュボード、ワークフローエディタ、ダイアグラムツールへの爆発的な需要
- 「Notionのようにして」や「Figmaのようにして」といった要件

### 🚀 技術的な利点
- **開発速度**：D3.jsと比較して5〜10倍速い開発
- **メンテナンス**：宣言的コードで理解しやすい
- **パフォーマンス**：必要な部分のみを再描画する効率的なレンダリング
- **スケーラビリティ**：ウィジェットベースのアーキテクチャで無限に拡張可能

## こんなチームに最適

✅ **複雑なダイアグラムや視覚化**を構築する必要があるチーム  
✅ **ノードエディタ、フローチャート、マインドマップ**を実装するチーム  
✅ **カスタムチャート**が必要なデータ視覚化チーム  
✅ D3.jsの複雑さに**疲れた**チーム  
✅ **Flutter経験**のある開発者がいるチーム  
✅ **パフォーマンスと開発生産性**の両方が重要なチーム
