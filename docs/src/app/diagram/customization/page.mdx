# Make it yours

Flitter Diagram follows the same idea as [Flitter Chart](/chart): the engine provides behaviour, and visual parts are widgets you own. `FlowDiagram` is a basic composition copied into your project. Its config is a convenient set of inputs for those starter widgets; your design can go beyond it by changing the widgets themselves.

Start with a [gallery example](/diagram/gallery) close to your use case. Each page shows the running diagram, its complete source and the exact builders to change.

## Know what you own

```text
flitter-ui/diagram                   Your project
─────────────────                   ────────────
Flow + FlowController               flow-diagram/index.ts
Graph state, measurement,           Assembles a starter style
hit testing and gestures            ├── config.ts
                                    └── parts/
Layout and path helpers                 node, edge, handle, background,
                                        controls, minimap, selection…
```

The engine supplies positions, measured sizes and interaction state. Your builders decide what to draw. The CLI copies the visual source; you can change its structure, introduce your own components and remove parts you do not need. Updating the engine dependency does not overwrite that source. Running the CLI with `--overwrite` does.

## Replace a composition

A node builder returns a Flitter widget. This example adds a title and a status using your own data; there is no need for a new `statusBadge` diagram option.

```typescript
import {
  Border, BoxDecoration, Column, Container, CrossAxisAlignment,
  EdgeInsets, MainAxisSize, SizedBox, Text, TextStyle,
} from "flitter-ui";
import { FlowDiagram } from "@/components/diagram/flow-diagram";

export const diagram = FlowDiagram({
  nodes: [{
    id: "review", type: "task", position: { x: 0, y: 0 },
    data: { label: "Review deploy", status: "Waiting for approval" },
  }],
  fitView: true,
  nodeTypes: {
    task: {
      build: ({ node, selected, hovered }) => Container({
        padding: EdgeInsets.all(16),
        decoration: new BoxDecoration({
          color: "#ffffff",
          border: Border.all({ color: selected || hovered ? "#6366f1" : "#cbd5e1", width: 2 }),
        }),
        child: Column({
          mainAxisSize: MainAxisSize.min,
          crossAxisAlignment: CrossAxisAlignment.start,
          children: [
            Text(String(node.data.label), { style: new TextStyle({ color: "#172033", fontSize: 15 }) }),
            SizedBox({ height: 8 }),
            Text(String(node.data.status), { style: new TextStyle({ color: "#d97706", fontSize: 11 }) }),
          ],
        }),
      }),
      handles: [{ type: "target", position: "left" }, { type: "source", position: "right" }],
    },
  },
});
```

The engine measures this widget, attaches the declared handles and wires selection and dragging. Add an image, compose a chart or return a `StatefulWidget` for local animation. Keep state in its `State` class and update it with `setState()`.

[Deployment workflow](/diagram/gallery/workflow) extends this into a branching pipeline with a toolbar action. [People and teams](/diagram/gallery/organization) uses the same mechanism for avatar cards.

## Change the whole visual system

| What you want to change | Where to work | Running example |
| --- | --- | --- |
| Node content and shape | `nodeTypes[name].build`, or your copied `parts/node.ts` | [People and teams](/diagram/gallery/organization) |
| Edges, labels and data encodings | `edgeTypes[name]`, `custom.edgeLabel`, `parts/edge.ts` | [Service traffic](/diagram/gallery/service-map) |
| Ports and connection feedback | Declared `handles`, `custom.handle`, `custom.connectionLine` | [Headless process loop](/diagram/gallery/headless) |
| Group containers and their children | A node builder plus `parentId` | [Grouped pipeline](/diagram/gallery/grouped-pipeline) |
| Placement and spatial composition | A `LayoutAlgorithm`, or positions you supply | [Resource board](/diagram/gallery/card-grid) |
| Background and selection visuals | `custom.background`, `custom.selectionBox`, `custom.nodesSelectionRect` | [Headless process loop](/diagram/gallery/headless) |
| Actions and surrounding UI | `nodeToolbar`, type-specific `toolbar`, `panels`, or your copied controls/minimap | [Workflow action](/diagram/gallery/workflow) |

`custom` supplies the shared visual builders. `nodeTypes` and `edgeTypes` select builders for named data types. In the starter, registered types take precedence: **replace `nodeTypes.default` to change untyped nodes**. Changing `custom.node` alone does not replace the starter's registered default builder. The same rule applies to `edgeTypes.default` and `custom.edge`.

Builder arguments provide `selected`, `hovered`, `dragging` and connection state where relevant. Use them to draw feedback. The engine owns the node/edge/handle gestures; a visual replacement does not need to reimplement them. Use `GestureDetector` for additional product actions, such as a toolbar button.

## Edit the copied source directly

Overrides are convenient when compositions share one starter. For a design used throughout your app, open the copied `flow-diagram/parts/` files and change them directly. `index.ts` is yours too: compose your own panels, choose your defaults and expose only the inputs your application needs.

`config.ts` belongs to that style. You can add tokens for your own parts or remove unused ones together with their consumers. To start with a completely different config type and no starter visuals, use [Headless Flow](/diagram/headless).

## Keep the contract, own the design

The engine still needs graph ids, declared handle geometry and path geometry for hit testing. Flitter widgets are the rendering contract; DOM or React elements are not returned from builders. When changing an edge's route, supply `edgeTypes[name].getPath` or `custom.edgePath` so drawing and hit testing use the same geometry. When drawing your own `CustomPaint`, implement both SVG and Canvas if you support both renderers.

These contracts keep the graph interactive while the appearance changes. [Builders & Context](/diagram/api) describes the data available to each part.
