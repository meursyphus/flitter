# Builders & Context

The diagram API follows [Flitter Chart](/chart/api): data goes into a headless engine, and builders turn its state and geometry into widgets. The copied `FlowDiagram` supplies a basic set of builders. Use them, edit their source or provide your own.

Start with the [gallery](/diagram/gallery) to see complete compositions. This page describes the contracts those examples use.

## Data

```typescript
import type { FlowNode, FlowEdge } from "flitter-ui/diagram";

const nodes: FlowNode[] = [
  { id: "review", type: "task", position: { x: 0, y: 0 }, data: { label: "Review", status: "waiting" } },
  { id: "ship", type: "task", position: { x: 240, y: 0 }, data: { label: "Ship", status: "ready" } },
];
const edges: FlowEdge[] = [
  { id: "review-ship", source: "review", target: "ship", type: "approval", data: { approved: false } },
];
```

`type` selects your builder. `data` holds the information that builder needs; the engine does not prescribe your card content. Positions may be supplied by a [layout algorithm](/diagram/api/layout). [Nodes & Handles](/diagram/api/nodes-and-handles) and [Edges](/diagram/api/edges) document the geometry and data contracts.

## Custom parts

Most visual builders have this shape:

```typescript
(args, context) => Widget
```

`Flow<TConfig>` requires a complete `FlowCustom<TConfig>`. The copied `FlowDiagram` accepts a partial `custom` and fills the rest from its own source. Its default builders are exported as `xyflowCustom`.

| Part | What the builder receives | What you provide |
| --- | --- | --- |
| `node` | `NodeBuilderArgs`: node data, selected, hovered, dragging, resizing, absolute position | Fallback node widget |
| `edge` | `EdgeBuilderArgs`: edge data, local path, size, endpoints, selected, hovered | Fallback edge widget |
| `edgeLabel` | Edge, label, selected, hovered, anchor `x`/`y` | Label widget or `null` |
| `handle` | Node, resolved handle, connectable, connecting/candidate flags | Connection handle widget |
| `defaultHandles` | Node and context | `HandleSpec[]` for nodes without declared handles |
| `connectionLine` | Connection state, local path, size, endpoints, validity | Connection preview widget |
| `background` | Viewport and pane width/height | Background widget or `null` |
| `selectionBox` | Selection rectangle in pane pixels | Selection widget |
| `nodesSelectionRect` | Selected nodes and their bounds in flow coordinates | Selection frame or `null` |
| `edgePath` | Edge (or `null` for a preview), endpoint params, path type | `EdgePathResult` used for both painting and hit testing |
| `resizeControl` | Node, position, line/handle variant, resizing | Resize affordance widget |
| `reconnectHandle` | Edge, endpoint and grab-area size | Endpoint affordance widget |

The engine wires node, edge and handle interactions. Builders draw the flags they receive. `Widget` means a Flitter widget, on either SVG or Canvas.

## Named node and edge builders

Use type maps when a diagram contains several kinds of content. Keys are application-defined strings.

| Extension | Contract |
| --- | --- |
| `nodeTypes[name]` | A node builder, or `{ build, handles?, toolbar? }` |
| `handles` | An array of `HandleSpec`, or `(node) => HandleSpec[]` |
| `toolbar` | `(args, context) => Widget \| null`, positioned beside the node |
| `edgeTypes[name]` | An edge builder, or `{ build, getPath? }` |
| `getPath` | `(params, edge) => EdgePathResult` for this type |
| `nodeToolbar` | Fallback toolbar for types without their own toolbar |
| `panels` | `{ position, child }[]` for your surrounding widgets |

**Builder lookup matters.** The engine uses the matching type, then a registered `default`, then `custom.node` or `custom.edge`. The starter registers default node and edge types. Override `nodeTypes.default` / `edgeTypes.default` to replace them, or use a new named type. A fallback override alone will not replace a registered type.

Handle lookup follows `node.handles`, then the resolved type's `handles`, then `custom.defaultHandles`. Declare `handles: []` explicitly for a type with no ports.

[People and teams](/diagram/gallery/organization) defines a `person` builder. [Service traffic](/diagram/gallery/service-map) defines a `traffic` edge. [Grouped pipeline](/diagram/gallery/grouped-pipeline) replaces the registered default node.

## Context

```typescript
type FlowContext<TConfig extends object> = FlowController & { config: TConfig };
```

| Available to builders | Use it for |
| --- | --- |
| `context.config` | Your style's inputs. Direct `Flow` accepts your own type unchanged. |
| `context.nodes`, `context.edges`, `context.viewport` | Read the current graph and view. |
| `context.getNode(id)`, `context.getEdge(id)` | Read an individual element. |
| `context.updateNodeData(id, data)`, `context.updateEdgeData(id, data)` | Apply application actions that update content. |
| `context.addNodes()`, `context.addEdges()`, `context.deleteElements()` | Change the graph from a toolbar or panel. |
| `context.fitView()`, `context.layout()` | Frame or rearrange the graph from your own controls. |

Keep builders free of state mutations while building. Call controller methods from event handlers. [Deployment workflow](/diagram/gallery/workflow) shows a toolbar action using `updateNodeData`. [Controller](/diagram/api/controller) documents lifecycle and persistence. Widgets built outside a builder can access the controller through `FlowProvider` in their Flitter build context.

## Override example

This complete composition replaces the default node. The engine continues to provide selection, hover and dragging.

```typescript
import { Border, BoxDecoration, Container, EdgeInsets, Text, TextStyle } from "flitter-ui";
import { FlowDiagram } from "@/components/diagram/flow-diagram";

export const diagram = FlowDiagram({
  nodes: [{ id: "task", position: { x: 0, y: 0 }, data: { label: "Your content" } }],
  fitView: true,
  nodeTypes: {
    default: {
      build: ({ node, selected, hovered }) => Container({
        padding: EdgeInsets.all(20),
        decoration: new BoxDecoration({
          color: "#ffffff",
          border: Border.all({ color: selected || hovered ? "#6366f1" : "#cbd5e1", width: 2 }),
        }),
        child: Text(String(node.data.label), {
          style: new TextStyle({ color: "#172033", fontSize: 16 }),
        }),
      }),
      handles: [{ type: "target", position: "left" }, { type: "source", position: "right" }],
    },
  },
});
```

To draw custom paths, reuse the copied `ShapePaint` helper or implement `CustomPaint`. `EdgeBuilderArgs.path` is in the edge widget's local coordinates; `origin` locates it in flow coordinates. Changing the route requires matching path geometry for hit testing. See [Edges](/diagram/api/edges).

## Compose the engine directly

Use [Headless Flow](/diagram/headless) when you want your own style assembly and config type. All visual builders are explicit there; no xyflow node types, controls or minimap are added automatically.

The starter's optional config conveniences are described in [Starter Style](/diagram/api/styling). Behavioural settings and callback signatures are available under the expandable reference in [Interaction](/diagram/api/interaction).
